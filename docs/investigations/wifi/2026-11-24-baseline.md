# Wi-Fi Investigation Baseline — 2026-11-24

## Scope and test environment

This is a sanitized summary of observations collected during the initial
investigation. Exact private network identifiers and raw logs are intentionally
not included. Test timestamps and some environmental details were not retained;
the measurements below should therefore be treated as preliminary evidence,
not a fully reproducible benchmark.

### Target device

- Device: FunnyPlaying Retro Pixel Pocket (blue unit)
- Hostname used during testing: `RPPBLUE`
- Firmware reported by user: `v1.1.3`
- OS release: RetroPixel 20251127 / CoreELEC-derived, VERSION_ID 2025.11
- Build date reported by OS: 2025-12-11
- Architecture: aarch64
- Kernel: Linux 4.4.189
- Wi-Fi adapter: Realtek RTL8188EUS, USB ID `0bda:8179`
- Wireless interface: `wlan0`
- Driver modules observed loaded: `r8188eu` and `8188eu`
- Network management: ConnMan and wpa_supplicant

### Comparison computer

- Arch Linux desktop/laptop
- Connected to the same unified home Wi-Fi network
- Computer used 5 GHz; handheld used 2.4 GHz

## Observed measurements

### Latency

| Path | Sample | Packet loss | Average | Maximum |
|---|---:|---:|---:|---:|
| Computer → router | 20 packets | 0% | 5.059 ms | 8.492 ms |
| Computer → handheld | 20 packets | 0% | 25.016 ms | 166.369 ms |
| Computer → handheld | 30 packets | 0% | 29.585 ms | 120.371 ms |
| Handheld → router | 20 packets | 0% | 34.9 ms | 158.9 ms |
| Handheld → router | 30 packets | 16% | 90.17 ms | 390.5 ms |
| Handheld → router | 30 packets | 6% | 63.672 ms | 246.986 ms |

After the user disabled Deco Fast Roaming and allowed the connection to settle:

- Handheld remained associated with the same observed access-point BSSID.
- Signal was approximately -49 dBm.
- Reported transmit bitrate was 150 Mbps.
- A 30-packet ping had 0% loss, average 18.655 ms, maximum 45.529 ms.

This is a promising before/after observation, but it does not establish that
Fast Roaming caused the earlier instability. Conditions and repeated samples
were not controlled sufficiently to establish causation.

### Wireless association

- The handheld associated on 2.4 GHz, channel 3 (2422 MHz).
- Signal readings during inspection were generally around -46 to -55 dBm.
- One short polling sample showed the same BSSID over approximately 60 seconds.
- Historical logs included disassociation/deauthentication events and subsequent
  association success messages.

### USB and kernel events

A kernel log captured a USB host-controller teardown and reinitialization:

- The DWC2 USB controller removed the USB bus.
- The Realtek USB Wi-Fi device disconnected.
- The USB controller registered a new bus.
- The Realtek device was detected again.
- The wireless driver initialized and the interface later became ready.

This establishes that at least one USB/controller reset occurred. It does not
establish what triggered it.

Other USB disconnect/reconnect events were also present in historical logs.

### Counters

- `ifconfig wlan0` showed cumulative RX dropped counters in the thousands.
- No corresponding RX errors were reported in those snapshots.
- `/proc/net/wireless` showed zero discarded counters in a later snapshot.
- These were cumulative snapshots, not controlled before/after counter deltas;
  they are not sufficient to attribute packet loss to the driver or radio.

## Controlled tests already attempted

### Driver power-management parameters

The following parameters were observed at baseline:

- `rtw_power_mgnt=2`
- `rtw_ips_mode=1`
- `rtw_enusbss=0`
- `rtw_smart_ps=2`

Temporarily setting `rtw_power_mgnt=0` and `rtw_ips_mode=0` did not produce
an improvement in the sampled ping. The original values were restored.

**Assessment:** This single test does not support those two parameters as the
sole cause. It does not rule out other power-management interactions.

### USB power control

The USB device's `power/control` was observed as `on` in one snapshot, with
`autosuspend` set to 2. A temporary USB power-control test did not improve
latency in the sampled run.

**Assessment:** No causal conclusion. A single noisy ping sample is insufficient
to evaluate USB autosuspend or controller power management.

### Fast Roaming

The user disabled Deco Fast Roaming. A subsequent 30-packet ping showed no loss
and lower latency than several earlier samples.

**Assessment:** Worth retaining as a test condition. Not confirmed as the root
cause; repeatable controlled comparisons are still needed.

## Invalid or incomplete measurements

### TCP throughput

An early custom TCP benchmark was invalid because it measured client-side send
buffer acceptance rather than confirmed receiver throughput. A later attempt
received only part of the expected payload before the connection closed, but
the test protocol and timeout behavior were not sufficiently validated.

**Do not use the earlier reported throughput figures as evidence.**

No reliable throughput benchmark has yet been established.

## Current hypotheses — not confirmed

1. **USB/controller interruption:** The captured DWC2 teardown and USB device
   disconnect may explain some Wi-Fi outages. The trigger is unknown.
2. **Power/suspend interaction:** The firmware's suspend path has previously
   been observed to unload/reload DWC2. This could interrupt USB Wi-Fi, but it
   has not been demonstrated to explain the captured event or all observed
   network instability.
3. **Wireless driver behavior:** The RTL8188EUS driver may contribute to latency,
   packet loss, or recovery behavior. Existing measurements do not isolate it.
4. **Access-point behavior:** Disabling Fast Roaming coincided with an improved
   ping sample. This needs controlled repetition before drawing a conclusion.
5. **Radio/channel conditions:** The handheld uses 2.4 GHz on channel 3. This is
   a possible environmental factor, but no interference measurement establishes
   it as a cause.

## Current state and next steps

- Fast Roaming is OFF, as confirmed by the user.
- Driver power-management parameters were restored to their original values.
- No firmware, kernel, module, driver, or persistent device configuration change
  has been made as part of this investigation.
- The next step is a read-only hardware/driver/USB baseline, followed by
  repeatable network measurements and correlation with kernel events.
